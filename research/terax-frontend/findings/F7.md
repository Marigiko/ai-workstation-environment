# F7: Integration Architecture Patterns

## Findings

### [1] LiteLLM Proxy acts as a universal OpenAI-compatible gateway that frontends connect to via standard `base_url` + `api_key` configuration, routing requests to 100+ LLM providers through a single endpoint
- quote: "OpenAI Proxy Server (LLM Gateway) to call 100+ LLMs in a unified interface & track spend, set budgets per virtual key/user"
- url: https://docs.litellm.ai/docs/simple_proxy
- source_type: primary
- published: 2026
- confidence: high

### [2] Aider integrates with any OpenAI-compatible backend by setting `OPENAI_API_BASE` and prefixing models with `openai/`, making it trivial to point a frontend at a LiteLLM proxy instead of a raw provider
- quote: "Aider can connect to any LLM which is accessible via an OpenAI compatible API endpoint... export OPENAI_API_BASE=<endpoint>... aider --model openai/<model-name>"
- url: https://aider.chat/docs/llms/openai-compat.html
- source_type: primary
- published: 2026
- confidence: high

### [3] The MCP client-server architecture separates the AI host application (MCP Host) from tool providers (MCP Servers), with each host creating one MCP client per server connection—this is the standard pattern used by Claude Code, VS Code, and Cursor
- quote: "MCP follows a client-server architecture where an MCP host — an AI application like Claude Code or Claude Desktop — establishes connections to one or more MCP servers."
- url: https://modelcontextprotocol.io/docs/concepts/architecture
- source_type: primary
- published: 2025-06-18 (spec version)
- confidence: high

### [4] MCP uses JSON-RPC 2.0 as the data layer protocol with dynamic tool discovery—clients call `tools/list` to discover available tools at runtime, then `tools/call` to execute them, enabling hot-pluggable tool ecosystems
- quote: "MCP defines three core primitives that servers can expose: Tools (executable functions), Resources (data sources), Prompts (reusable templates)."
- url: https://modelcontextprotocol.io/docs/concepts/architecture
- source_type: primary
- published: 2025-06-18
- confidence: high

### [5] MCP supports two transports: Stdio (local process communication, no network overhead) and Streamable HTTP (remote servers with SSE streaming)—frontends should abstract this so users don't need to know which transport an MCP server uses
- quote: "Stdio transport: Uses standard input/output streams for direct process communication between local processes on the same machine. Streamable HTTP transport: Uses HTTP POST for client-to-server messages with optional Server-Sent Events for streaming capabilities."
- url: https://modelcontextprotocol.io/docs/concepts/architecture
- source_type: primary
- published: 2025-06-18
- confidence: high

### [6] LiteLLM's MCP Gateway provides a fixed endpoint (`litellm_proxy`) for all MCP tools with permission management by Key/Team/User, effectively acting as a centralized MCP hub that frontends connect to—eliminating the need for each frontend to manage MCP server connections individually
- quote: "LiteLLM Proxy provides an MCP Gateway that allows you to use a fixed endpoint for all MCP tools and control MCP access by Key, Team."
- url: https://docs.litellm.ai/docs/mcp
- source_type: primary
- published: 2026
- confidence: high

### [7] Aider connects to Ollama via the `OLLAMA_API_BASE` environment variable (default `http://127.0.0.1:11434`) and uses `ollama_chat/<model>` prefix, with auto-sizing of context windows to prevent silent data discard—a pattern all frontends should follow
- quote: "Ollama uses a 2k context window by default, which is very small for working with aider. It also silently discards context that exceeds the window. By default, aider sets Ollama's context window to be large enough for each request."
- url: https://aider.chat/docs/llms/ollama.html
- source_type: primary
- published: 2026
- confidence: high

### [8] LiteLLM routes requests through: User Request → Virtual Key Auth → Rate Limiting → Router (load balancing/fallbacks/retries) → litellm.completion() (OpenAI format translation) → Post-request async logging/spend tracking—this is the canonical request lifecycle for AI gateway architecture
- quote: "Request Flow: User Sends Request → Virtual Keys → Rate Limiting → LiteLLM proxy_server.py → LiteLLM Router → litellm.completion() / litellm.embedding() → Post-Request Processing (Logging, Spend Tracking)"
- url: https://docs.litellm.ai/docs/proxy/architecture
- source_type: primary
- published: 2026
- confidence: high

### [9] LiteLLM provides built-in RAG endpoints (`/rag/ingest` and `/rag/query`) that handle the full pipeline: Upload → Chunk → Embed → Vector Store, supporting OpenAI, Bedrock, Vertex AI, and S3 Vectors backends through a unified API
- quote: "All-in-one document ingestion pipeline: Upload → Chunk → Embed → Vector Store... After ingesting documents, use /rag/query to search and generate responses with your ingested content."
- url: https://docs.litellm.ai/docs/rag_ingest
- source_type: primary
- published: 2026
- confidence: high

### [10] The A2A (Agent-to-Agent) protocol is emerging as the standard for agent interoperability—LiteLLM acts as an A2A gateway supporting both 0.3 and 1.0 wire formats, enabling frontends to invoke external agents through a unified proxy layer with trace grouping and spend attribution
- quote: "LiteLLM follows the A2A (Agent-to-Agent) Protocol for invoking agents. LiteLLM proxy routes A2A agents using a2a-sdk 1.x and can serve either A2A 0.3 or 1.0 wire format to clients per agent."
- url: https://docs.litellm.ai/docs/a2a
- source_type: primary
- published: 2026
- confidence: high

### [11] The dominant integration pattern for AI coding tools is: Frontend → OpenAI-compatible proxy (LiteLLM) → Multiple LLM providers, where the proxy handles auth, routing, load balancing, cost tracking, and MCP tool orchestration—the frontend only needs to speak OpenAI protocol
- quote: "Aider can connect to any LLM which is accessible via an OpenAI compatible API endpoint."
- url: https://aider.chat/docs/llms/openai-compat.html
- source_type: primary
- published: 2026
- confidence: high

### [12] MCP's notification system enables dynamic tool ecosystems—servers send `notifications/tools/list_changed` when available tools change, and clients re-fetch the tool list, meaning frontends must handle hot-reloading of tool capabilities without restart
- quote: "The server can proactively notify connected clients... Upon receiving this notification, the client typically reacts by requesting the updated tool list."
- url: https://modelcontextprotocol.io/docs/concepts/architecture
- source_type: primary
- published: 2025-06-18
- confidence: high
